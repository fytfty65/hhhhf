# OmniRoute 四季沉浸式登录门户：可执行方案

日期：2026-11-14。状态：基于仓库源码检查的设计与实施计划；尚未制作场景资产、修改前端或执行性能测试。

## 1. 结论与范围

目标是达到参考图的精细环境美术观感，并让四季变化、移动端体验和完整认证流程适合 OmniRoute。

推荐路线：**Blender 精细场景母版 → 同机位四季渲染与模型导出 → 浏览器分层动态场景 → 有需要时增强局部实时 3D**。这条路线同时保留真正的建模资产与高质量的网页呈现。默认网页使用固定构图；如果明确要求自由绕看、可交互物体和连续几何变化，则采用第 7 节的实时 3D 版本。

参考截图可以确认画面构图、材质观感和季节差异，不能确认原站采用 Three.js、离线动画还是生成视频，也不能从三张截图恢复原始模型和动画。目标应是复现视觉品质与空间关系，并制作 OmniRoute 自己的场景，而不是承诺逐像素还原。所附图片作为视觉参考，不将其中品牌、按钮或文字视为产品需求。

本轮范围为未登录首页 `/` 的门户。登录后的大厅、规划地图与工作台不铺设常驻 3D 背景；可以在后续独立任务中延续色彩与小尺寸季节元素。

## 3. 视觉方向：四季云上驿站

保留参考图的吸引力：近景大树框景、暖光木屋、悬浮平台、云海远山、冷暖光照和不同深度的季节粒子。为旅行产品增加地图、背包、指南针、旅行手账，角色如需出现则设计原创的旅行伙伴。

桌面构图以 16:9 为主：左侧约 0–58% 是树、木屋和浮岛，中央到右侧为层叠云海；右侧约 64–94% 留出低细节登录安全区。避免大树、摆动秋千、近景落叶穿过表单。左侧标题控制在两行：

> 把四季，走成我们的旅程。
>
> 让目的地、预算和同行者的期待，在同一份行程里相遇。

这只是品牌叙事建议；现有认证按钮与状态文案第一轮保留，以保持用户认知和测试契约。参考图的大标题位于正中，但项目需要常驻登录表单，因此重新分配场景与文字空间。

顶栏保留 OmniRoute 标志；右侧放四季选择、跟随日期和动态开关。不要将装饰圆点描述为实时服务健康。底栏显示当前季节和简短旅行文案。现有两条功能介绍压缩成简短信息；成都示例路线可下移到第二屏，首屏给场景和表单留空间。

登录卡推荐稳定的烟灰玻璃外壳，输入区域拥有足够实底。按钮沿用品牌橙，季节色只改变环境和辅助装饰。普通文字对比度至少 4.5:1，大号文字至少 3:1；春季亮景与冬季雪地均需复核。输入框建议 16px 字号，触控目标至少 44px。卡片取消跟随鼠标倾斜，视差只作用于环境。

## 4. 真正达到参考质感的资产工作

### 4.1 同一份场景母版

在 Blender 建立米制场景，锁定物体位置、主相机、焦距与主体轮廓。先用灰模叠加实际登录卡验证空间，再精修资产。建议起始镜头约 35–50mm，最终以构图评审为准。另做竖屏机位，不能只依赖横图 `cover` 裁切。

| 资产 | 必须表现的细节 | 制作方式 |
| --- | --- | --- |
| 主树 | 不规则树干、根系、枝叉、树皮裂纹、苔藓 | 高模细节烘焙到低模；树冠按枝叶簇组织 |
| 木屋 | 屋檐厚度、错落木板、窗框、屋顶材质、暖光 | 模块建模、木纹方向一致；窗光独立控制 |
| 浮岛 | 地表厚度、岩层断面、根须、草地与石块接触 | 主轮廓建模，局部散布草叶与碎石 |
| 旅行道具 | 背包布料、手账、地图、杯具、路牌 | 中景可辨识、少量叙事物件 |
| 远山与云海 | 山峰层次、空气透视、云层厚度 | 高质量离线渲染；网页远景以背景板承载 |
| 季节元素 | 春花、夏叶、秋落叶、冬积雪 | 同一树枝骨架，独立叶簇与雪层资产 |

关键不是单纯增加面数，而是轮廓、接触阴影、材质尺度、粗糙度变化、逆光边缘与前中后景的分离。主物体应有真实厚度；冬季屋顶、树枝、台阶上的积雪应改变轮廓，不只是调白颜色。

### 4.2 材质与灯光

制作木材、树皮、岩石、植被、布料、雪的 PBR 材质。高低模流程包括 UV、法线、粗糙度、AO；浏览器共享主体优先 1K–2K 纹理图集。颜色贴图使用 sRGB，法线/粗糙度/AO 使用线性数据。烘焙光照与浏览器实时光照避免重复叠加。

统一太阳方向与主构图，四季主要调光色、雾、植被和地表；窗内暖光作为连续叙事锚点。采用明确色彩管理与曝光，确保离线背景板和网页 3D 前景处于同一视觉体系。不要用全屏高强度 Bloom 代替光照细节。

### 4.3 四季变化清单

| 季节 | 几何/材质变化 | 光照与动态 |
| --- | --- | --- |
| 春 | 嫩叶、少量花簇、湿润石面、浅绿地表 | 温暖晨光、轻雾、少量花瓣 |
| 夏 | 浓密叶簇、深绿草地、较高植被覆盖 | 明亮天光、轻风、慢云；萤火仅用于夜景扩展 |
| 秋 | 叶色分布变化、部分稀疏枝条、地面落叶 | 金色侧光、少量近景叶片和远景落叶 |
| 冬 | 落叶枝、屋顶和地面独立雪层、覆霜石面 | 冷蓝环境、暖色窗光、细雪 |

所附参考没有明确单独的春景样本；春季由同一母场景扩展，先验证与其余三季的一致性。

### 4.4 必须交付的资产

- 可继续编辑的 `.blend` 母场景、纹理源文件、相机与灯光配置、资产来源/授权清单。
- 四季桌面主视觉与四季移动主视觉，建议母图至少 2560×1440、1080×1920；网页输出多尺寸 AVIF/WebP。
- 每季 4–6 个分层元素：天空远山、云海、主体、前景等；每层包含被遮挡区域的补全及视差外扩边缘。
- 每季完整 poster 作为加载首帧与失败兜底；不能用无图空白作为默认状态。
- 如需局部实时 3D：共享低模 GLB、季节叶簇/雪层、压缩纹理、LOD 和动画片段。
- `manifest` 记录版本、尺寸、季节、桌面/移动资源、焦点、层深、文件体积与备用路径。

AI 图片可用于早期风格探索；四季独立生成容易导致窗户数量、树枝和物体位置漂移，不能直接视为同场景成品。若采用生成图路线，需要锁定底图、局部编辑、分层补全和逐季对齐；它仍不能替代可编辑 3D 模型。

## 5. 网页呈现：三档共享同一套美术资产

| 档位 | 使用对象 | 内容 |
| --- | --- | --- |
| 静态 | 减少动态、用户关动态、节省流量或故障回退 | 当季 poster + 完整 DOM 登录表单 |
| 标准（默认） | 手机、平板与普通桌面 | 分层场景、轻视差、低密度云雾/粒子 |
| 增强 | 性能足够的桌面且资源加载成功 | 标准远景 + 局部 Three.js 模型、树叶风动与雪层变化 |

默认先显示 poster 和表单，再解码并增强场景；认证完成前不让场景加载延长已有的会话恢复等待。已登录直达大厅时，不额外下载登录场景包。

标准档可以使用 HTML 分层图片与 CSS transform，轻量 Canvas 绘制粒子。只有需要深度图或实时模型时才动态导入 Three.js。不要同时保留两套持续绘制的背景；替换成功后卸载旧 SVG 动画。

2.5D 的边界：允许约 6–14px 的小幅分层视差，不承诺侧面绕看和完整遮挡变化。深度图只作局部增强，强位移会暴露边缘拉伸和空洞。春夏秋冬的结构一致可让交叉渐变平滑；落叶和积雪的拓扑变化不应靠高透明度叠加硬撑。

## 6. 四季控制与交互规则

季节状态从背景组件移到唯一的控制器，所有图层、粒子、文案共同读取。建议状态包含 `mode`（日期/手动/演示）、`season`、`targetSeason`、`motionEnabled`、`quality`、`assetStatus`。

- 日期模式：默认按浏览器本地日期使用北半球月份划分，3–5 月春、6–8 月夏、9–11 月秋、12–2 月冬。明确这是氛围季节，不是真实天气。未来扩展半球选项；不为装饰背景申请定位权限。
- 手动模式：春夏秋冬可点选，持久化用户偏好并提供“跟随日期”恢复入口。
- 演示模式：用户主动开启后每季停留约 20–30 秒，过渡约 1.8–2.4 秒；登录默认不每 11 秒换季。保留暂停控制。
- 输入框聚焦、提交中或密码重置时暂停自动换季和明显视差；手动切换不清空输入、不重挂载表单、不改变焦点。
- 资源准备完成才提交视觉切换；失败继续显示当前季节并保留重试。控件选中状态不能先变为冬季而画面仍显示春季。
- 快速连点采取“最新目标优先”：只保留一个过渡事务，取消旧任务或忽略过期解码结果。
- 四季的 `key` 不能放到整个 `AuthPortalScreen` 上；只允许背景内部切换。
- 页面隐藏时取消 rAF 和计时器；恢复时重置时间基准，避免粒子跳跃。
- 监听系统减少动态设置的实时变化；静态模式无持续帧循环，必要时按需绘制一次。
- 切换季节不自动播报大量装饰文字；四季按钮有可读名称和 `aria-pressed`，动态开关可键盘操作。

不默认播放声音、不绑定陀螺仪、不用鼠标控制整个登录卡。

## 7. 如果要求完整实时 3D

这一档应以第 4 节资产为基础，另做浏览器优化。共享主体用 GLB，LOD 降低面数；树叶采用实例化，材质合并并限制透明叠层；远景仍可用背景板。Three.js 足够完成首版，无需同时引入多个场景框架。

季节变化采用共享材质参数插值、树叶出现/消失的遮罩，以及独立雪层的覆盖变化。冬季使用有厚度的雪几何，不能只有表面朝上的白色 shader。静态接触阴影优先烘焙，少量动态物体用受限阴影；云海优先预渲染或低成本平面，避免全屏体积光线步进。

压缩资源可以选 Meshopt 和 KTX2/Basis，但先验证当前 Three.js 加载器与生产 CSP。解码器和 WASM 同源部署；如果实际解码依赖 WASM 编译权限，仅在验证后增加最小 `wasm-unsafe-eval` 权限及相应测试，不能为模型随意开启通用 `unsafe-eval`。

首轮增强档预算可从可见三角形 15–30 万、draw call ≤100、DPR ≤1.5 开始；这些是原型调优起点，不是跨设备性能保证。透明叶片和云雾的填充开销常比面数更重要。若连续数秒低于 30fps，先降分辨率与粒子，再转标准档；增加滞回，防止频繁升降档。

模型加载失败、WebGL 不支持或 context lost 均立即回到匹配的 poster，认证流程继续可用。退出登录页必须释放纹理、geometry、material、renderer、ResizeObserver、事件监听和 rAF，避免与大厅地图竞争 GPU。

### 必须保持的认证行为

1. 账号登录继续通过 `apiFetch('/api/auth/login')`，`setAccessToken` 后调用既有 `onLoginSuccess`。
2. 注册成功仍返回登录 Tab，显示既有成功提示，不能暗中改成自动登录。
3. 游客仍走现有注册随机账号再登录流程；不要把现有行为变成没有持久化的假体验按钮。
4. 找回密码保留 forgot → reset 两阶段和原错误处理。
5. 普通用户进入大厅，管理员进入 `/admin`；会话恢复和刷新 cookie 策略不因换肤变动。
6. 保持 `auth-login-tab`、`auth-register-tab`、`auth-nickname`、`auth-username`、`auth-password`、`auth-submit`、`auth-trial`、`auth-forgot` 及现有 `reset-*` 标识。
7. 背景 `aria-hidden` 且 `pointer-events:none`；季节控制是独立 DOM。Canvas 不承载输入框或主按钮。
8. 表单加载、错误、成功提示、浏览器自动填充、键盘提交和重试均可正常使用。

当前游客说明存在“行程保存在这台设备”的文字，而游客流程实际创建后端账号。新视觉不扩散这句话；涉及文案修正时以已实现的存储及账号升级行为为准，不承诺未验证的数据迁移。

## 9. 响应式与登录状态覆盖

- ≥1200px：场景叙事与表单分列，表单宽约 400–432px，主视觉占左侧；以实际文字长度控制间距。
- 768–1199px：压缩标题与叙事信息，允许单列居中；表单不压到树屋主体上。
- <768px：使用专门竖屏构图，顶部保留品牌和少量场景，表单为主体；关闭鼠标视差，粒子减量或静态。
- 使用 `min-height:100svh`，允许文档纵向滚动；不要固定整页高度导致注册或重置按钮被裁切。
- 移动键盘弹出只调整可用空间和滚动位置，不不断重建相机/Canvas；照顾安全区域。
- 输入框建议适配自动填充和 16px 字号，避免 iOS 聚焦缩放。场景与系统明暗主题独立，四季均使用验证过的门户配色。

必须检查 360×800、390×844、768×1024、1366×768、1440×900、1920×1080，以及手机横屏、200% 缩放。每类至少覆盖登录、注册、错误提示、重置请求、设置新密码五种形态。

## 10. 加载、性能与资源预算

以下为验收目标，需在约定设备与网络上实测后调整，当前没有达标测量结果。

| 项目 | 初始目标 |
| --- | --- |
| 首屏当季 poster | 桌面 ≤450KB，手机 ≤220KB；压缩以保留纹理为前提 |
| 默认首屏环境资源 | ≤1.5MB，不包含既有应用 JS；可交互前不下载另外三季完整资产 |
| 当季标准档增强 | 桌面约 2–4MB 上限，手机约 0.8–1.5MB；首屏后逐步加载 |
| 实时增强包 | 另设约 4–8MB 起始预算，按模型与纹理总量核算；不阻塞登录 |
| 帧率 | 约定桌面目标 55–60fps；手机标准档稳定 30fps 或自动静态 |
| Web Vitals | 指定环境目标 LCP ≤2.5s、CLS ≤0.1；发布后观测 p75 INP ≤200ms |
| 动态关闭或隐藏页 | 无持续场景更新；恢复与退出不泄漏资源 |

加载策略：当季 poster 解码成功即可展示；只预取可能使用的下一季，节省流量模式不做预取。手动目标未就绪时保留当前画面。最多同时保留当前和下一季的大纹理，其他降级为压缩文件缓存。注意 4K RGBA 纹理单张基础内存约 32MiB，含 mipmap 更高，不能用下载 KB 数代替 GPU 内存预算。

同源静态资源使用版本化路径和验证过的缓存头。只有路径真正不可变才使用长期 immutable 缓存；不要套到会被覆盖的 manifest。预加载或优先级 API 以本地 Next.js 文档为准。日期首次解析避免 hydration 不一致：先稳定占位/首图，再在客户端选择；必要时由服务端传入明确时区与日期种子。

## 11. 实施里程碑与时间估算

估算假设：一名前端、一名熟悉 Blender 的环境美术，可复用部分已授权基础材质，有两轮视觉反馈。人日不是自然日；渲染排队、素材采购和评审等待另计。

| 阶段 | 工作与交付 | 预计投入 | 通过条件 |
| --- | --- | --- | --- |
| P0 构图验证 | 桌面/竖屏灰模、真实登录卡占位、四季色彩脚本 | 1–2 人日 | 树屋与表单互不遮挡，手机构图成立 |
| P1 单季美术样板 | 先做秋季完整精修静帧与材质细节 | 3–5 人日 | 与参考同尺寸评审，树皮/木屋/云海达到目标后再扩季 |
| P2 四季资产 | 共享母场景扩春夏冬，分层/竖屏/压缩导出 | 3–5 人日 | 无结构漂移，积雪与植被变化可信 |
| P3 标准档接入 | 布局、季节状态、分层动效、完整认证适配 | 3–4 人日 | 五类表单形态及所有认证路径可用 |
| P4 质检与发布准备 | 设备性能、失败回退、无障碍、回归、录屏 | 2–3 人日 | 验收矩阵和性能目标通过 |
| P5 可选实时增强 | 低模烘焙/GLB、KTX2、动态模型、分档和销毁 | 额外 5–10 人日 | 比标准档增加有价值的空间交互，且不拖慢登录 |

标准版合计约 12–19 人日，两角色部分重叠时可按 2–3 周排期；从零制作复杂角色、精细原创树屋或增加多轮反馈需重新估算。完整实时版本在此基础上追加优化时间。资源准备好的功能原型可能更快，但不能把功能原型当成参考级美术完成。

每个阶段产出可检查文件。P1 是画质门槛：如果一张静帧都达不到要求，不提前堆粒子和转场。技术性能原型可与美术准备并行，但不改变这一验收顺序。

## 12. 验证与完成定义

### 视觉

四季各保存桌面和手机截图，另保存一段至少覆盖完整四季循环的录屏。采用同视口对照参考：树皮/木板细节、物体接触阴影、云海纵深、积雪厚度、前景遮挡和文字可读性。截图相似度分数不能代替人工美术检查。

### 功能

登录成功/失败、注册再登录、游客入口、密码重置、管理员跳转、刷新恢复会话都要验证。输入账号密码后切四季，值和焦点保持；请求中换季不重复提交；资源 404、超时、解码失败和 WebGL 丢失不阻断认证。

### 工程

从 `front` 目录执行 `npm run typecheck`、`npm run lint`、`npm run test:node`、`npm run build`；执行已有 core-flow、refactor-regression 以及新增 seasonal-auth E2E。Playwright 当前默认启动 production server，需先完成 build，并确认 3001 端口上的服务确实是当前版本，避免复用旧构建形成假通过。

日期映射、手动优先级、最新目标获胜、暂停恢复与失败保留当前季节适合纯逻辑测试；布局通过有意义的交互截图与人工检查，不为每条 CSS 写镜像断言。现有测试不足以证明四季对比度，应增加门户的无障碍检查和最亮/最暗画面人工核验。

桌面 Chrome/Edge、iOS Safari、Android Chrome 至少各有一次真实设备或明确记录局限的验证。模拟手机视口不能替代真实 GPU、触控键盘和内存检查。对照改造前后的冷启动、INP、场景退出后内存与帧活动，性能回归超预算则降低档位。

### 发布与回退

用可配置开关保留旧门户渲染入口；开关只影响呈现，不改变认证协议。资源部署和页面版本配套发布，先验证资源可达再开启。构建时开关需要重新构建才能回退；若要求即时切换，应采用受控运行时配置并明确缓存策略。完成前记录回退方式和静态兜底截图。

## 13. 推荐执行决定

先交付一张达到参考质感的秋季主视觉及其移动构图，再扩展同场景四季；以分层动态标准档上线，按明确的交互价值决定是否加入实时 3D。这样可以把美术品质、登录效率和设备覆盖分别验收。

“超越参考”的具体目标是：原创旅行叙事、日期/手动/演示三种季节模式、连续一致的四季场景、手机专用构图、完整可访问认证流程与低性能自动降级。最终画质是否超越，需要实际产出的素材与运行画面对照评审；本方案不将尚未制作的效果表述为已经实现。
