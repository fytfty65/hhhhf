# 类别判定 bug：同一个「面」字，第二处受害者（2026-10-08）

## 一句话

`_coarse_category`（类别判定）把**风景名胜判成了饭点**，根因与 anchoring 那批**完全同一个**：
地址里的单字「面」。影响的不是内部数字，而是**抽查表的"类别"列 —— 人就是照着那一列打分的**。

## 怎么发现的

修完 anchoring 后我去核 `work/` 下待看的人工抽查表，在
[review-库尔勒-kel4.md](<OminRoute/OminRoute/work/review-库尔勒-kel4.md>) 里看到一行：

```
| D2 | … | 博斯腾湖风景名胜区 | 餐饮 | ¥42（票务平台价，非官方） | … | 高德资料：风景名胜｜评分 4.6 …
```

**类别写"餐饮"，可它自己的资料栏写着"风景名胜"。** 抽查表是给人打分的，
这一列错了会直接把审阅人带偏 —— 所以这不是洁癖，是评测工具本身的正确性问题。

## 根因（逐字核到，不是推测）

`_coarse_category` 把 `name + type + **desc** + tags` 拼成一段文本去套关键词，且**不过滤单字**：

```
desc = "高德资料：风景名胜｜评分 4.6｜巴音郭楞焉耆盆地东南面博湖县境内"
                                                        ↑
food 关键词组含单字「面」→ 命中 "东南面" → 判成 food
```

而 `PREFERENCE_TAXONOMY` 的 dict 顺序里 **food 在 scenic 之前**，于是地址里的一个字
压过了节点自己写的 `type="风景名胜"`。

第二种写法同样中招（与 anchoring 那批一模一样）：
「巴楚镇新村路(巴楚博物馆后**面**)」→ 判成 food。

复现：
```powershell
cd ai-service
.\venv\Scripts\python.exe -u ..\work\dbg_coarse_category.py   # 逐关键词打出命中位置
```

## 修法

1. **结构化 `type` 优先**：它就是平台给的分类，比拿文本猜可靠得多；
2. **`desc` 不参与**关键词匹配（那里有地址）；
3. **单字关键词一律不用**（与 `_is_anchor_side` 同一口径）；
4. 类别归一复用 `node_contract.CATEGORY_ALIASES` —— **唯一一把尺子**，
   不再让 `plan_quality` 和 `node_contract` 各有一套。

### 中间踩的坑（修一个错引出另一个错）
第一次为了避开单字陷阱给关键词加了"≥2 字"过滤，结果 `food` 组里**只有单字「餐」**，
「餐饮服务」这种高德类型名直接掉成 `other`。所以第 4 条改用权威别名表认类型名。
回归测试 `test_amap_service_type_names_are_recognised` 钉住了这一点。

## 影响量化

对全部已录方案复算（122 份、1772 个节点）：

| 项 | 数值 |
| --- | --- |
| 类别判定改变 | **24 个节点**，涉及 17 份方案 |
| 变化类型 | 全部是 `food → scenic`（无一例外） |

### ⚠️ 更重要的发现：旧尺子在**虚高**分数

受控 A/B（同一份方案跑两遍、只换 `_coarse_category`）：

- 15 份方案分数**下降**，最多 **−2.90**，平均 **−0.17**。

原因：把风景名胜当成饭点，等于虚报了"餐饮多样性"，**让方案看起来比实际更均衡**。
所以旧分数是虚高的，新分数更低但**更真**。

### ⚠️ 排名翻转：过去的模型对比结论需要重看

按"城市+节点数"分组（组内才是可比对象）核对修复前后的排名：

| 组 | 结果 |
| --- | --- |
| 库尔勒-16 | **排名翻转**：`kel2..kel8` 从高于 `turbo*` 掉到低于 `turbo*` |
| 库尔勒-18 | **排名翻转**：`kel1` 从组内第一掉到第七 |
| 其余 4 组 | 无翻转 |

原因：`kel*` 那批方案含被误判的节点而 `turbo*` 不含（或含得少），
所以修复对它们的影响不成比例 —— **同一组内不同变体受到的偏差量不同**，
这正是排名会翻转的原因。

复现：
```powershell
.\venv\Scripts\python.exe -u ..\work\ab_category_scores.py       # 净影响
.\venv\Scripts\python.exe -u ..\work\check_category_ranking.py   # 排名是否翻转
```

> 踩坑记录：`check_category_ranking.py` 第一版用正则 `(.+?)-(\d+)\.json` 取组名，
> 把变体名也带进了组名，于是每组只剩 1 个成员、"可比组 0 个"，
> 脚本却打印了 `✓ 排名全部不变` —— **空集上的假通过**。
> 已改成按 `城市-节点数` 正确分组，并且**没有可比组时明确报"没验证到任何东西"**，
> 不许把空集当通过。

## 诚实记录：我在这一批里弄坏了 3 个标题

重新生成时 `plan_title()` 取不到 `city`/`trip_days`（方案里只有 `trip_days=2`），
回退成默认的「方案 A」，**把 3 张表的手写标题覆盖了**。
我的 diff 只比对了 `| D` 数据行，没覆盖标题，所以没拦住。

- `kel1`、`kel4` 的标题已按我本轮读过的原文恢复；
- `kel3` 的括号说明**无法从方案 JSON 恢复**（没有 city/intent 字段），
  `work/` 也未纳入 git、没有备份 —— 已在表内**如实标注"无法恢复、不猜也不编"**，
  而不是编一个看起来合理的说明。

脚本已修：重新生成时把旧标题原文传给 `--label`，且比对范围扩到非表格行。
这个教训与项目既有纪律一致：**没验证到的差异不要假设不存在**。
